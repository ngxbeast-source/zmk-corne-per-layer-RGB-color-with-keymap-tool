# RGB Layer Setup Guide

*The new RGB tool helps a lot with this.*

**Any new layers get defined in `corne-rgb.dtsi`, along with an assigned color.**  
New formats are defined below; we no longer have to use the "standard" ZMK formatting, and can add to the code much easier using these new syntaxes and variables.  
A template is set up for your use in the appropriate areas within the `.dtsi` so you can better understand the layouts of this file.

---

## Order of Operations
**IMPORTANT:** In your `.keymap` add `#include keyboard_rgb.dtsi` to the top of the file; where all the other `#inldue`s are.

1. Just `#define` a layer, the name does't matter. What's important is the number. This number is what ZMK relates the new varible (the new defined layer name) to the layers in the keymap.
1a. Then `#define` a color for the "layer" (we are using a "new" define, RGB_LAYER), these will be used for our "new" colors and "return" colors.
2. Build your macros following the structure from the helpers, **then** build your hold-tap behavior, if making a momentary layer.
3. Then you can use these new behaviors in ZMK Studio for "hold-tap" funcitons.

---

## New Modular Structuring

- ``#define MO_RGB_MACRO(node_name, node_label, layer, NEWCOLOR, RETURNCOLOR)``
  
  *This macro defines the "new" momentary layer's color.*

- ``#define HT_RGB(node_name, node_label, macro_ref)``
  
  *This behavior defines the "new" momentary layer macro's function; used in conjunction with the above to get momentary LEDs. WITH a configurable keypress. This is our new hold-tap for our colored layer.*

- ``#define TO_RGB_PRESS_MACRO(node_name, node_label, layer, NEWCOLOR)``

  *This is used for our "combo gateways" to access new sub-base layers. We use the press function for proper RGB behavior.*

- ``#define TO_RGB_MACRO(node_name, node_label, layer, NEWCOLOR)``

  *This is for our subbase layers, OR our combos, and should be used for building the actual "sub-base's", the layers we access from the "gateway", color functions.*

- **IF ANYTHING REMAINS UNCLEAR, ALWAYS REFER TO THE ORIGINAL `.dtsi` FOR CLARITY/IDEA OF THE CODE STRUCTURE.**

### Making a Momentary Layer/SubLayout (NMRW, XTRA, GFUN)

1. Define the layer  
2. Define the RGB color  
    *Get color codes here: [colorizer.org](https://colorizer.org/)*
3. Build the MACRO using:

   ```c
   MO_RGB_MACRO(node_name, "ZMK_Studio_Description", LAYER_, NEWCOLOR, DEFAULT_COLOR)
   ```
4. Build the BEHAVIOR using:

   ```c
   RGB_HT(node_name, node_label, macro_ref)
   ```
   - `macro_ref` is your `MO_RGB`, `node_name`
5. Map the new RGB_HT BEHAVIOR `node_name` into your `.keymap` / or in ZMK.studio

---

### Making a TOGGLED Layer/SubBase (TGLR1 & TGLR2)

Uses a similar approach (not to be confused with ZMK's "ToggleLayer"). TGLR1 & TGLR2 are TOGGL**ED** Layers and **cannot** be activated until we are in the *Gateway*.

- Use:
  ```c
  TO_RGB_MACRO(node_name, "ZMK_Studio_Description", LAYER_, NEWCOLOR)
  ```
  Then map the new macro `node_name` to your keymap, either in your files or ZMK.Studio.

---

### Making a Gateway (GAMETGL & TGL)

- Use:
  ```c
  TO_RGB_PRESS_MACRO(node_name, "ZMK_Studio_Description", LAYER_, NEWCOLOR)
  ```
  This is used mostly exclusively for Gateways, since the RGB behaves differently on Gateways when switching to a TOGGLED LAYER.

---

I personally use these on combos, allowing for a "hidden" out-of-the-way Gateway activation. This makes navigation between different BaseLayers much more accessible.

*I had issues making the `&to` TOGGLE LAYER RGBs work properly, so I opted for a more direct approach.*

#### Example Flow:

- COMBO → MENU → SELECTED LAYER
- SAME COMBO → BACK MENU; or PRESS AGAIN → "BASE" LAYER 

(In the BaseLayer there's a gameCombo to access our GameLayer; Pressing the gameCombo again, you can go back to the base layer, **or** press the GatewayLayer Combo to access the GAMEGatewayLayer. Then, from the GAMEGatewayLayer pressing the GatewayLayerCombo again returns you to the GameLayer.)

*This shows how the same combo can provide different functions depending on how you code the layer conditions for the combo.*  
*This is an important design for allowing the RGBs to change fluidly, without overcomplicating the keypresses. **Path the combos CORRECTLY to fit your layouts!***

## Layer Types

So now we can think about our layers in 3 ways:

- **(Sub)BaseLayer:** a layer that you want to "stay on"
- **Gateway:** a layer whose only function is exclusively used as to "toggle" different BaseLayer(s)
- **MomentaryLayer/Sub-Layouts:** a layer that acts as "sub-layout" when a key press is held

This will help you understand which *Macros*, *Behaviors*, and *Combos* to utilize when building your RGB Layers.

## Blink Key (optional)

New visual macro to know if you toggled caps lock, or num lock, (note: this isn't persistant it just gives a quick flash as a visual cue).
- Fairly simple; it's a `tap-dance` behavior with our chosen key(s) hard-coded into the macros.
```c
        /* BLINK Tap dance */
        td_numcaps: td_numcapsBLINK {
            compatible = "zmk,behavior-tap-dance";
            #binding-cells = <0>;
            tapping-term-ms = <300>;
            bindings = <&kp LSFT>, <&c_blink>, <&n_blink>;
```
This is our helper for the "Blink Sequence"; it flashes 3 times, the "color" is programable with the "ON"(new color), and the "OFF"(return color) helpers, the "WAIT" is the time between "actions"/blinks; I use 80ms since anything too low and the blinks just don't look right, you can fiddle around with this number to fit your needs. we are just toggling the lights on and off, WHILE the "new" color is active. Then when the sequence is over, the macro brings us to the "return" color (whatever you color your "working layer" is).
```c
#define BLINK_SEQ(ON, OFF, WAIT) \
    &macro_tap &rgb_ug ON \
    &macro_wait_time WAIT \
    &macro_tap &rgb_ug RGB_TOG \
    &macro_wait_time WAIT \
    &macro_tap &rgb_ug RGB_TOG \
    &macro_wait_time WAIT \
    &macro_tap &rgb_ug RGB_TOG \
    &macro_wait_time WAIT \
    &macro_tap &rgb_ug RGB_TOG \
    &macro_wait_time WAIT \
    &macro_tap &rgb_ug OFF
```
This is the "color" of your blink.
```c
#define N_BLINK_ON   RGB_COLOR_HSB(0,100,60)     /* Num On - Bright Red */
#define C_BLINK_ON   RGB_COLOR_HSB(200,100,60)   /* Caps On - Cyan */
```
- You can make multiple of these to fit whatever key you want to press, I mainly use this for CapsLock and NumLock `tap-dance` function, or you can make a universal blink function that can be programmed in the ZMK tool.
```c
#define KP_BLINK(node_name, node_label, key, blink_color, return_color, wait) \
         ZMK_MACRO(node_name, \
            label = node_label; \
            bindings = <&macro_tap &kp key>, \
            <BLINK_SEQ(blink_color, return_color, wait)>; \

KP_BLINK(c_blink, "CAPS LOCK + BLINK", CAPS, C_BLINK_ON, RGB_ABC, 80)
KP_BLINK(n_blink, "NUM LOCK + BLINK", KP_NUMLOCK, N_BLINK_ON, RGB_ABC, 80)
```
- Next, is a "bindable" blink function that I use to inidcate any windows combos. For instance, I have a program that I disable with a windows combo, so to tell if that function is activated I tied a "blink" to it.

```c
#define BLINK_ON     RGB_COLOR_HSB(39,100,75) // BLINK Color

    blnk: blnk {
        compatible = "zmk,behavior-macro-one-param";
        label = "Configurable Blink Macro";
        #binding-cells = <1>;
        wait-ms = <0>;
        tap-ms  = <0>;
        bindings = <
            &macro_param_1to1
            &macro_tap &kp MACRO_PLACEHOLDER
            BLINK_SEQ(BLINK_ON, RGB_XTRA, 80)
        >;
```
Last we have a momentary blink macro that I use for "temp layers", you could probably bind this with a "&to" function but I haven't messed around too much with it. I use this only for my function keys. Still experimental, sometimes LEDs dont "change back" when you press the layer too quickly; Potential fix? might be to add a "return" color at the end of the macro.
```c
#define MO_BLINK(node_name, node_label, layer, blink_color, return_color, wait) \
        ZMK_MACRO(node_name, \
            label = node_label; \
            bindings = <&macro_press &mo layer BLINK_SEQ(blink_color, return_color, wait)>, \
                       <&macro_pause_for_release>, \
                       <&macro_release &mo layer>; \
```

## Notes
- **DO NOT** have "higher layers" go to lower layers (i.e., `12 -> 2`)
- **Even in your `.keymap`**
- It's good practice to have "sub-layouts" below the "base" (e.g., `GAME -> GFUN`)
